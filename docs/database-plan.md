# Хранение и масштабирование

Рабочая версия использует SQLite. Режим PostgreSQL доступен через `APP_STORAGE=postgres` и `DATABASE_URL_FILE`. Проверка на PostgreSQL 17 переносит архив двух тестовых объектов, сверяет суммы, повторно импортирует смету и редактирует отчёт под учётной записью мастера. Она также проверяет запрет чтения строк другого объекта на уровне базы.

`compose.postgres.yaml` добавляет PostgreSQL 17 к основному Compose и хранит данные в постоянном томе. Порт базы доступен в сети Compose. Владелец схемы создаёт роль приложения с правом входа, без прав суперпользователя, создания ролей и обхода политик строк. Пароли и строка подключения хранятся в `deploy/secrets`.

Для тестового переноса сделайте архив командой `python scripts/data_archive.py backup <архив>`. Укажите владельцу новой пустой базы `POSTGRES_OWNER_URL` и запустите `python scripts/migrate_postgres.py --archive <архив> --app-role m100_app --files-root /app/data`. Скрипт проверяет число строк по объектам и финансовый итог каждого дня до фиксации транзакции. Файлы из `imports/` перенесите из архива в каталог данных приложения. Проверьте архив и журнал переноса перед включением нового режима.

## Сначала измерения и небольшие изменения

- Проверить SQLite integrity/foreign_key_check и периодически проверять восстановление архива.
- Перед WAL проверить установленную версию SQLite и наличие исправлений известных ошибок WAL. Сохранять `synchronous=FULL`, установить предел ожидания блокировки и контролировать checkpoint/размер WAL. Не размещать SQLite на сетевом диске.
- Через EXPLAIN QUERY PLAN подтвердить индексы для `entries(date,item_id)`, `reports(sync_status,retry_at)`, `audit(date,created_at)`, `projects(owner_id,created_at)` и журнала напоминаний `created_at`. Добавлять индекс под существующий запрос, учитывая стоимость записи.
- Заменить построение истории через отдельный запрос на каждый день на пакетное чтение с группировкой. Добавить пагинацию и ограниченные фильтры, измерять время/API P95 на реальных объёмах.
- Держать внешние HTTP-запросы вне транзакций, сохранять версии отчётов и идемпотентность отправки. Кешировать справочники по версии, а не бессрочно.
- Несохранённый текст в React — отдельный черновик. Для защиты от закрытия WebView нужен автосохраняемый черновик пользователя/объекта/дня; он не должен считаться отправленным отчётом и подавлять напоминание.

## Когда переходить на PostgreSQL

Несколько экземпляров API, регулярная конкуренция записей, большая история или отдельный сервер БД — основания для миграции. Для нынешних VPS с 1 ГБ RAM PostgreSQL, приложение и обработка больших документов на одной машине дадут нежелательную конкуренцию за память. Под нагрузку разумнее выделить ресурсы отдельно.

Целевая схема: users, projects, project_members, source_tables, positions, daily_reports, report_lines, report_revisions, synchronization_jobs, reminder_schedules, notification_deliveries. Все рабочие строки связаны с project_id, права проверяются сервером; денежные величины используют NUMERIC, объёмы — отдельную точность. Нужны foreign keys, уникальный отчёт на объект/дату, уникальные задания отправки и индексы под фильтры. Версии схемы — Alembic; соединения — ограниченный пул, резервные копии — с проверкой восстановления.

Миграция: заморозить запись, сделать копию, перенести идентификаторы, таблицы и настройки, сверить количество строк и финансовые итоги по каждому объекту/дню, выполнить проверки доступа, затем переключить API. До успешной проверки сохранить возможность возврата. Переезд БД не должен одновременно менять финансовые формулы и права пользователей.

Источники: [SQLite WAL](https://sqlite.org/wal.html), [SQLite Backup API](https://sqlite.org/backup.html), [настройка памяти PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-resource.html).
